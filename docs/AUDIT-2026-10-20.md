# Lawyard v2 — Project Audit (2026-10-20)

Scope: full repo read-through, git history (75 commits, all on `main`, no merged PRs),
static checks (`tsc --noEmit`, `eslint .`), auth/RLS/middleware review, API route and
payment-flow review, dependency and repo-hygiene review.

**Baseline (clean):** `tsc --noEmit` passes with 0 errors. `eslint .` passes with
**0 errors / 181 warnings** (mostly `no-explicit-any`, `<img>` instead of `next/image`,
and one `react-hooks/set-state-in-effect` in `components/theme-provider.tsx`).
Type safety and lint discipline are in decent shape — the problems below are
architecture / authorization / process problems, not "the build is broken".

---

## Critical

### C1. Any logged-in user can promote themselves to admin (privilege escalation)

Three pieces combine into a full admin takeover:

1. `schema.sql:83` — the only UPDATE policy on `profiles`:
   ```sql
   CREATE POLICY "Users can edit own profile" ON profiles FOR UPDATE USING (auth.uid() = id);
   ```
   No `WITH CHECK`, and **no column restriction on `role`**. PostgREST will happily
   accept `PATCH /rest/v1/profiles?id=eq.<own-uid>` with `{"role":"admin"}` using the
   public anon key plus the user's own JWT.
2. `supabase/migrations/20260615000004_sync_role_to_jwt.sql` — a `SECURITY DEFINER`
   trigger copies `profiles.role` into `auth.users.raw_app_meta_data`. So the
   self-promotion is also written into the user's JWT.
3. `middleware.ts:78` gates `/admin` on `user.app_metadata?.role !== 'admin'`, and
   `lib/supabase/admin-auth.ts` gates every admin server action on
   `profiles.role === 'admin'`. Both now pass.

`app/admin/actions.ts` then exposes `deleteArticle`, `deleteCoupon`, `verifyLawyer`,
`rejectCorporatePost`, `createCoupon`, etc. to that user.

**Fix:** split the policy and pin the mutable columns. Two options:
- Column-level `GRANT UPDATE (full_name, phone, ...) ON profiles TO authenticated;` and
  revoke table-wide UPDATE, or
- a `WITH CHECK` that pins the sensitive columns, e.g.

```sql
DROP POLICY "Users can edit own profile" ON profiles;
CREATE POLICY "Users can edit own profile"
  ON profiles FOR UPDATE TO authenticated
  USING (auth.uid() = id)
  WITH CHECK (
    auth.uid() = id
    AND role = (SELECT role FROM profiles WHERE id = auth.uid())
    AND subscription_tier = (SELECT subscription_tier FROM profiles WHERE id = auth.uid())
    AND subscription_status = (SELECT subscription_status FROM profiles WHERE id = auth.uid())
  );
```

Also stop deriving admin identity from a user-writable table for authorization
decisions — read `app_metadata` (or a dedicated `admin_users` table) in both places,
so there is **one** source of truth.

### C2. Unauthenticated key/token exposure in git history (rotate now)

`project_structure.md` was committed on **2026-05-23** (`5b22224`) containing real
values, then redacted on **2026-06-15** (`68d280f`):

```
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIs...
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOiJIUzI1NiIs...
```

Both are still recoverable from history (`git show 5b22224:project_structure.md`).
The **service role key bypasses all RLS** — this is the single highest-impact item.

**Fix:** rotate the Supabase JWT secret / service role key and the anon key in the
Supabase dashboard immediately; update Vercel env vars. History rewriting is optional
cleanup — rotation is what actually closes it. Then add a pre-commit secret scanner
(e.g. `gitleaks protect --staged`) so this cannot recur.

### C3. `/api/auth/hook` is an unauthenticated mail relay with HTML injection

`app/api/auth/hook/route.ts` accepts any POST and, with no signature check at all,
sends a Brevo transactional email to whatever `payload.user.email` says:

```ts
export async function POST(request: NextRequest) {
  const payload = await request.json()
  const userEmail = payload?.user?.email   // attacker-controlled
  ...
  await sendTransactionalEmail({ to: [{ email: userEmail }], ... })
```

Impact: (a) send unlimited branded mail from `tobi@lawyard.org` to any address —
phishing vector and Brevo quota/domain-reputation burn; (b) `token_hash` is
interpolated into `href="${confirmationUrl}"` **without URL encoding**, so a crafted
`token_hash` breaks out of the attribute and injects arbitrary HTML into an email
that arrives from your domain.

Note the sibling route `app/api/auth/send-email/route.ts` **does** verify an HMAC
(`AUTH_SEND_EMAIL_HOOK_SECRET`). Two competing hooks, one secured, one not.

**Fix:** delete whichever hook is not wired in Supabase; enforce the standard
Supabase hook signature (`Authorization: Bearer ${AUTH_HOOK_SECRET}`) on the survivor;
`encodeURIComponent(tokenHash)` and allowlist `redirect_to` to your own origins.

## High

### H1. Vercel cron points at a route that doesn't exist — subscriptions never expire

`vercel.json`:

```json
{ "path": "/api/cron/expire-subscriptions", "schedule": "0 0 * * *" }
```

The handler lives at `app/directory/api/cron/expire-subscriptions/route.ts`, i.e.
`/directory/api/cron/...` on the main host or `/api/cron/...` **only on
`directory.lawyard.org`**. `middleware.ts` explicitly excludes `/api` from the
directory rewrite, so `/api/cron/expire-subscriptions` on the main domain 404s.

Result: paid subscriptions never downgrade. Silent revenue leak.

**Fix:** either add `"path": "/directory/api/cron/expire-subscriptions"`, or move the
route to `app/api/cron/expire-subscriptions/`, and add a health check that asserts a
200 from the cron endpoint.

### H2. `verifyPayment()` can be replayed for free, forever

`app/directory/actions/payments.ts`:

```ts
export async function verifyPayment(reference: string) {
  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return { error: 'Not authenticated' }
  ...
  const { data: tx } = await sbAdmin.from('transactions').select('*').eq('reference', reference).single()
  // no tx.user_id === user.id check
  // no tx.status check
  if (isSuccess) { /* tier from tx.plan_name applied to user.id, expiresAt = now + 365d */ }
```

No ownership check and no already-processed check. A user who paid once can call
`verifyPayment("<their reference>")` repeatedly — Paystack keeps reporting `success` —
and regenerate a fresh 365-day entitlement each time. It also lets any authenticated
user act on **another** user's reference.

**Fix:** in the server action, require `tx.user_id === user.id` and bail if
`tx.status === 'completed'`; move all entitlement side effects to the webhook only,
and make the action a read-only status poll.

### H3. Two Paystack webhook handlers, divergent behaviour

Both exist and do the same job differently:

| | `app/api/webhooks/paystack` | `app/directory/api/webhooks/paystack` |
|---|---|---|
| Signature compare | `timingSafeEqual` (correct) | `hash !== header` (non-constant-time) |
| Re-verifies with Paystack API | yes | **no** |
| Transaction status written | `'success'` | `'completed'` |
| Metadata source | `event.data.metadata` | `tx.metadata` (DB) |

They disagree on the status vocabulary, and they read metadata from different places.
Critically, `createPayment()` in `payments.ts` inserts DB metadata as
`{ authorization_url }` only — **it never stores `type`** — so the directory webhook's
`meta?.type === 'chamber_subscription'` can never be true for those rows and a chamber
payment would be applied to `profiles` instead of `chambers`.

Paystack has one webhook URL per account, so one of these is dead-but-maintained code
that could silently take over on a config change.

**Fix:** keep one handler (the `/api/webhooks` one — it verifies and is constant-time),
fold the `extra_post` / `service_request` / `course_enrollment` branches into it,
derive the payment type from the DB row rather than the event, and delete the other.

### H4. Payment bypass on `service_requests`

`supabase/migrations/20261016000003_service_requests.sql`:

```sql
CREATE POLICY "Clients manage own service requests"
  ON service_requests FOR ALL TO authenticated
  USING (auth.uid() = client_id)
  WITH CHECK (auth.uid() = client_id);
```

The client owns the row, so a direct PostgREST call can set
`status = 'requested'` without paying and rewrite `booking_fee` to `0`. The server
action is the only thing enforcing payment; RLS is not.

**Fix:** make it `FOR SELECT` for clients, and restrict client UPDATE to the
non-financial columns (or add a `WITH CHECK` that pins `status`/`booking_fee` to
their previous values). State transitions belong to the service role.

### H5. Unauthenticated upload endpoint writing to a public bucket

`app/api/upload/corporate-posts/route.ts` requires **no authentication** and uploads
with the service role to the `brand-press` bucket:

```ts
if (!file.type.startsWith('image/')) ...
const ext = file.name.split('.').pop()
const filePath = `brand-press/${crypto.randomUUID()}.${ext}`
```

- unbounded storage cost / free image host for anyone on the internet.
- `ext` comes from the client filename while only the MIME string is checked, so
  `image/svg+xml` + `.svg` is accepted → arbitrary SVG served from your storage
  origin (script execution if ever framed or served same-origin).
- This was introduced by commit `68d280f`, titled *"address security review
  findings — Upload API: remove auth requirement"*. A security fix that removed
  a control.

**Fix:** require an authenticated session (and a paid/entitled one), allowlist
`image/png|jpeg|webp` only, derive the extension from the detected MIME, cap size,
and rate-limit per user.

## Medium

- **Open redirect via the `redirect` form field.** `app/directory/login/actions.ts`
  does `destination = redirectParam` then `redirect(destination)` with no validation.
  `//evil.example` is protocol-relative to a browser. Validate with
  `startsWith('/') && !startsWith('//')` — here and in `signup()`.
- **`x-forwarded-host` trusted in redirect construction.** `app/directory/auth/callback/route.ts`
  builds `https://${forwardedHost}${redirectTo}`. Vercel sets this header, so risk is
  low today, but it is the classic host-header open redirect if the app is ever put
  behind another proxy. Compare against an allowlist of known hosts.
- **Cron auth has an `undefined` fallback.** `app/directory/api/cron/...` compares
  `authHeader !== \`Bearer ${process.env.CRON_SECRET}\`` — if the env var is missing,
  the expected value becomes the literal string `Bearer undefined`. Fail closed when
  the secret is unset.
- **Dead CAPTCHA-bypassing login route.** `app/api/auth/login/route.ts` has no callers,
  calls `signInWithPassword` with no Turnstile token and no rate limit, and sets
  session cookies on the *request* object only (`request.cookies.set`) so it never
  issues a `Set-Cookie` on the response — it is broken *and* an unthrottled
  credential-stuffing surface. Delete it.
- **No rate limiting anywhere.** `grep -rn "rateLimit"` returns nothing. Login,
  signup, magic link, coupon validation, review submission and the upload route all
  rely on Supabase's defaults alone.
- **`approve_lawyer` records the wrong reviewer.** In
  `app/api/slack/interactions/route.ts`, verification rows get
  `reviewed_by: verification.user_id` — the applicant, not the admin. Audit trail is
  wrong. (The same pattern is copied in `deny_lawyer`.)
- **`profiles` may be over-exposed.** `CREATE POLICY "Public profiles are viewable by everyone" ON profiles FOR SELECT USING (true)` combined with `profiles.email` means
  every user's email is readable by anyone holding the anon key. Confirm whether that
  is intended; if not, move `email` out of `profiles` or restrict the policy.

## Low / code quality

- **Session refresh cost in middleware.** `supabase.auth.getUser()` runs on every
  non-directory request (a network round-trip). Fine, but it is the hot path for all
  traffic — consider scoping the matcher to routes that need auth.
- **`host.startsWith('localhost')`** makes local dev always resolve to the directory
  site; `/dashboard` becomes `/directory/dashboard` locally while `/admin` does not.
  Dev/prod divergence, easy to trip over.
- **650-line `if`-chain** in `app/api/slack/interactions/route.ts` — one giant handler
  with a repeated `fetch(responseUrl, {replace_original: ...})` block eight times.
  Extract `ack()`, one handler per `action_id`, and a map from action to handler.
- **732-line `app/(main)/page.tsx`** and **585-line `app/directory/dashboard/page.tsx`** — dump-and-run pages; split into sections/components.
- **57 `any` / `as any`** in app code, concentrated in `lib/admin/api.ts` (16 warnings
  alone). Supabase's generated DB types would remove most of them.
- **Duplicated shells:** `components/Header.tsx` vs `components/directory/Header.tsx`
  (506 lines) and `components/Footer.tsx` vs `components/directory/Footer.tsx` are
  near-copies, as are the two `api/webhooks` routes. This is what produced H3.
- **Unused dependencies:** `resend` (0 imports — the project moved to Brevo, and
  `package.json` still carries it), `tw-animate-css`, `shadcn`, `radix-ui`,
  `@radix-ui/react-slot`. Removing `resend` in particular avoids a future dev
  "fixing" the email stack back to it.
- **`SECRET_KEY = process.env.PAYSTACK_SECRET_KEY!` at module scope** in
  `app/api/webhooks/paystack/route.ts` — the `!` is a TS-only assertion; if the var is
  missing, `createHmac('sha512', undefined)` throws. Read it inside the handler and
  fail with a 503.
- **`JSON.parse(body)` unguarded** in `app/directory/api/webhooks/paystack/route.ts`
  (the sibling route wraps it). Signature is checked first, so low severity, but it is
  a 500 on malformed input.

## Repo hygiene & process

- **No tests at all.** Zero `*.test.*` / `*.spec.*` files. The money paths
  (`verifyPayment`, entitlement grants, post caps) have no coverage; every fix above
  is a regression waiting to happen a second time.
- **No CI.** No `.github/` directory — nothing runs `tsc` or `eslint` before merge.
  Both pass today, but only because someone ran them by hand.
- **Build artifacts and agent state are committed:**
  `tsconfig.tsbuildinfo` (also in `.gitignore`, so it is tracked-but-ignored — the
  ignore is effectively dead), and **18 `.omo/run-continuation/*.json` session files**
  under `.omo/`, which is *also* in `.gitignore`. Remove both from the index:
  `git rm --cached tsconfig.tsbuildinfo .omo -r`.
- **Git hygiene:** 75 commits, all directly on `main`, zero pull requests, and
  security-relevant changes shipped inside 121-file commits (see `164510d`, +5,890
  lines). A security review cannot reasonably happen at that granularity — which is
  how a commit titled "address security review findings" shipped an unauthenticated
  upload endpoint.
- **Documentation sprawl and drift.** Seven root-level markdown files
  (`README.md`, `CHANGELOG.md`, `HANDOFF.md`, `TIMELINE.md`, `SESSION-SUMMARY.md`,
  `project_structure.md`, `system_architecture_read_me_reference_patterns_start_here_todo_documentation.md`)
  plus seven under `docs/`. They already contradict the code: `docs/FEATURE-STATUS.md`
  marks the auth hook as *"new, uncommitted"* for a file that is committed and live.
  `project_structure.md` is the file that leaked keys and is now a stale, secret-shaped
  document. Consolidate to `README.md` + `docs/`; delete the rest.
- **`schema.sql` is stale.** It only defines 9 tables while 16+ exist via migrations
  (`transactions`, `coupons`, `reviews`, `post_credits`, `plans`, `service_requests`,
  `course_enrollments`, `chamber_admins`, `app_settings`, `bookmarks`, …). Anyone
  reading it as the schema source of truth — including the RLS review this audit had
  to do manually — will miss policies. Either regenerate it from the DB or delete it
  in favour of `supabase/migrations/`.
- `scripts/migration-drift.mjs` exists and is good — but it is `pnpm run check:migrations`,
  invoked by hand, with no CI to run it. Wire it into CI (or a pre-push hook) and it
  pays for itself.

## Suggested order of work

1. **Rotate the Supabase service role + anon keys** (C2) — minutes, highest impact.
2. **Lock down `profiles.role`** (C1) and consolidate admin identity to `app_metadata`.
3. **Delete/secure the `/api/auth/hook` route** (C3) and the dead `/api/auth/login` route.
4. **Fix the cron path** (H1) — one line, restores subscription expiry.
5. **Make `verifyPayment` ownership- and idempotency-checked** (H2); collapse the two
   webhooks into one (H3).
6. Tighten `service_requests` RLS (H4) and the upload route (H5).
7. Then the process layer: CI with `tsc` + `eslint` + `check:migrations` + `gitleaks`,
   first tests around `verifyPayment` and the webhook, and prune the tracked artifacts.
